# Winstem — Supabase Setup

Winstem uses three Supabase services:

1. **Authentication** — email/password accounts, sessions, password recovery
2. **PostgreSQL** — profiles, files, folders, shares, notes, settings, activity
3. **Storage** — the actual file bytes in private buckets

All SQL you need ships with the repo under `supabase/`:

| File | What it does |
|---|---|
| `supabase/setup.sql` | **Run this one file** — schema + policies + storage combined |
| `supabase/schema.sql` | Tables, triggers, indexes (part 1 of setup.sql) |
| `supabase/policies.sql` | Row Level Security policies (part 2) |
| `supabase/storage.sql` | Buckets + storage policies (part 3) |

---

## Step 1 — Create the project

1. Sign in at [supabase.com](https://supabase.com).
2. **New project** → pick a name (e.g. `winstem`) and a strong database password.
3. Wait for provisioning (a minute or two).

## Step 2 — Run the SQL

Open **SQL Editor → New query**, open `supabase/setup.sql` from the repo,
paste its contents, and run. That single file applies the schema, RLS policies
and storage buckets in the correct order.

> ⚠️ **Why one file?** The pieces have dependencies: `policies.sql` and
> `storage.sql` reference tables that only exist after `schema.sql` runs. If you
> run them individually out of order you get errors like
> `relation "public.files" does not exist`. `setup.sql` avoids that entirely.

Everything is idempotent where practical (`CREATE TABLE IF NOT EXISTS`,
`DROP POLICY IF EXISTS`), so re-running `setup.sql` is safe.

## Step 3 — Auth settings

1. **Authentication → URL Configuration**
   - Site URL: `https://<user>.github.io/<repo>/` (or your custom domain)
   - Add the same URL to **Redirect URLs**
2. **Authentication → Providers → Email**
   - Enable **Confirm email** for production (users must verify before signing in).
   - Optionally enable **Secure email change**.
3. **Authentication → Settings → Session**
   - Default expiry of 3600s with refresh is fine; adjust to taste.

## Step 4 — Grab the public keys

**Project Settings → API**:

| Value | Where it goes |
|---|---|
| Project URL | `js/config.local.js` → `supabaseUrl` |
| `anon` / `sb_publishable_...` key | `js/config.local.js` → `supabaseAnonKey` |

Copy `js/config.local.example.js` → `js/config.local.js` and fill both in.

> The **service_role** key is listed on the same page. **Do not** put it anywhere
> in the frontend, in `config.local.js`, or commit it to git.

---

## Step 5 — Verify

In the Supabase dashboard:

- **Authentication → Users** — new sign-ups appear here
- **Table Editor → profiles** — one row per user, auto-created by trigger
- **Storage → Buckets** — `winstem-files` and `winstem-avatars` exist and are private

---

## Buckets

| Bucket | Access | Used for |
|---|---|---|
| `winstem-files` | Private, per-owner RLS | All user files |
| `winstem-avatars` | Private, per-owner RLS | Profile pictures |

Winstem never exposes files through a public bucket. Downloads and share links use
**signed URLs** generated by the frontend with the user's session.

## Backups

Supabase provides automatic daily backups on paid plans. On the free tier, export
your schema via **Database → Backups → Export** or simply keep the `supabase/*.sql`
files in git (they are the source of truth).
